# Computer Use 首期隔离工作区方案

日期：2026-11-02。用户明确要求先由 Weavelo 对话自主完成 GUI 重构，再继续 Computer Use；Computer Use 从首期锚定更强隔离。本方案替代此前“先在宿主会话完成语义控制，隔离作为后续可选扩展”的实施顺序。

用户随后要求 Octendra 自身同步继续开发。Weavelo GUI 由其对话独立推进；Octendra 已实现工作区真实身份、默认隔离路由和不可变观察。Mac Studio 的官方 Virtualization 持久来宾已完成实际安装、启动、SSH 读取/编辑/执行、双向文件传输与休眠恢复。新的私有 virtio 控制链路已通过来宾 Agent 执行日志完成真实画面、点击、中文/emoji 输入、快捷键保存与文件内容验收；三次动作的宿主焦点、光标和剪贴板修订均未变化。自动登记来宾、托管服务安装、正式网页 MCP 接入和全节点部署仍须闭环，不能把单机验证包视为全网升级完成。手动远控宿主功能保留，Computer Use 的默认执行目标是明确的 AI 工作区。

## 首期必须隔离的状态

AI 工作区要有独立的显示、输入目标、应用与浏览器数据和稳定的运行身份。用户在宿主操作时，AI 的点击、拖动、快捷键和文本不得落到宿主界面。工作区持久存在，应用、登录和任务成果不随一次工具调用或网络重连而被重建。

桌面虚拟机提供独立来宾系统和输入环境。Android 的专用 profile 与可信显示隔离应用数据及操作空间，但仍共享系统内核和部分系统服务，不能标为虚拟机同等级隔离。虚拟显示、浏览器 profile、嵌套 compositor、额外显示器和 macOS Spaces 都不能单独作为完整隔离的证明。

## 各平台首期路线

| 平台 | 首期路线 | 启动前必须核实的事实 |
| --- | --- | --- |
| Apple silicon Mac | Apple Virtualization framework 管理持久 macOS 来宾；通用 Linux 任务可采用对应 Linux 来宾 | 实际系统支持、虚拟化 entitlement、签名、可用存储与内存、来宾安装介质和实际图形输入 |
| Windows | 在独立 Windows 来宾中执行原生 Windows 任务，满足条件时优先既有 Hyper-V | Windows 版本和虚拟化功能、硬件能力、来宾许可与镜像、真实图形捕获和输入。不能假定 Home 版本有 Hyper-V |
| Linux | KVM 加完整 Linux 来宾，来宾内按实际桌面运行 compositor / AT-SPI | /dev/kvm 实际访问、CPU 架构、图形后端和资源；容器或宿主嵌套 compositor 不代替默认系统隔离 |
| Android 真机 | 核实专用且可用的工作资料或应用实例空间，并结合可信 AI 显示、按目标输入和局部状态管理 | profile 与 App 的安装、解锁和授权状态，OEM 显示能力、IME、剪贴板及音频的真实隔离范围 |
| 无法提供相应空间的设备 | 如实列为首期隔离尚不可用，继续定位该设备的具体实现条件 | 不静默退回用户宿主输入，不擅自转移到另一设备；需要整机隔离的 Android 任务明确选择专用执行设备 |

平台路线是待实施选择，尚未证明这些节点全部满足条件。先盘点现有能力，每类设备固定一个最小可交付后端；不同时搭多套自动兜底，也不以新建 Desktop 或多一个输出接口代替实际隔离。

依据：[Apple Virtualization](https://developer.apple.com/documentation/virtualization)、[macOS 来宾](https://developer.apple.com/documentation/virtualization/running-macos-in-a-virtual-machine-on-apple-silicon)、[Hyper-V 条件](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/host-hardware-requirements)、[QEMU 系统虚拟化](https://www.qemu.org/docs/master/system/)、[Android work profile](https://developer.android.com/work/managed-profiles)。

## 最小实现结构

宿主 Octendra 服务负责工作区的登记、启动、状态和恢复。来宾中的已注册 Agent 负责本机应用观察与执行；使用既有设备组、连接、文件传输、操作日志、构建和签名机制。Weavelo 把它呈现为一个真实的 AI 工作区来源，继续使用原生媒体和单流窗口。

工作区描述至少包含宿主设备、实际执行设备、执行上下文身份、隔离边界、当前状态和可用输入能力。来宾是可辨认的执行节点，不能伪装成宿主上原来那份应用。Android 描述包含实际 user/profile、应用实例和显示归属。

调用端仍使用 ui_observe / ui_act。设备发现提供明确的 AI 工作区目标，进入 Computer Use 默认选择它；第一次解析就返回真实执行位置，此后 observation_id 和 operation_id 绑定该位置、generation 及来源修订。选择过的目标不因掉线或缺少 App 自动切到宿主或别的机器。

AX、UIA、AT-SPI、浏览器语义接口和像素输入在工作区内部使用，以提高定位和操作可靠性。它们不再承担证明宿主与 AI 完全隔离的责任。需要明确操作宿主已有窗口时，使用单独标识的宿主来源，不能作为隔离任务失败后的隐式退路。

## 数据与连续使用

- 每个已配置工作区使用自己的持久系统盘、应用数据和浏览器 profile，不为每个动作或对话新建空白环境。
- 不默认映射整个宿主 home，不自动同步宿主剪贴板、麦克风、系统音频或浏览器 Cookie。任务输入与成果通过既有受授权文件通道传送，需要的目录或资源按任务实际范围连接。
- 连接授权继续复用。来宾内真实登录、OS 权限和签名身份单独核验，不复制宿主 TCC 数据库或假定宿主许可自动继承。
- 浏览器与应用正常启动、关闭和登录状态保留，不声称能将宿主正在运行的同一进程和全部内存状态无损搬进来宾。
- 工作区初始化和启动由服务自动管理，不把 hypervisor 命令、session、lease 或每动作批准暴露给模型。真正缺少的 OS 条件报告具体原因，不增设工具业务审批。

## 生命周期和恢复

工作区至少有未准备、启动中、可用、正在恢复、空闲和不可用状态，状态归宿主服务所有。应用任务、媒体消费者和工具请求的寿命分开；关 Weavelo 预览不销毁工作区，切网不重装环境。

宿主开机恢复管理服务。工作区按任务和观看需求启动；没有活动任务时才考虑休眠，不因 Agent 思考、等待页面事件或连接短暂波动中断工作。系统和产品更新沿用正式安装路径直接维护同一个持久环境，不增加发布分支、层层版本门禁或新的回退工程。

宿主、来宾或 helper 重启使对应原生代际失效。恢复后先确认真实执行位置与来源，再观察；结果未知的旧动作继续查原操作，不重放输入。虚拟机管理命令成功、系统启动、Agent 在线、应用可操作和实际出帧分别记录。

## 首期交付顺序

1. Weavelo 优先完成管理主界面、单流远控窗口、统一操作栏和系统菜单快捷入口，由其对话独立推进与汇报；Octendra 按用户后续指示同步开发隔离基础，不等待 GUI 完成才写代码。
2. Computer Use 实施开始时先完成 O7：盘点各目标机器，做出持久隔离工作区和真实图形输入的最小运行实例。优先在 Mac Studio 验证桌面完整链路，同时按目标平台分别验证可行性，不把 Mac 结果算作 Windows / Linux 通过。
3. O1 将该工作区的真实执行身份接入通用接口、不可变观察和资源调度。O2 / O3 完成 Android 的专用实例、显示、IME 与任务生命周期；O4 / O5 在隔离空间内完善桌面及网页语义。
4. Weavelo W1 到 W3 对接工作区来源、原生画面、输入和接管。GUI 重构不等待这些能力全部完成，也不因 Computer Use 计划改写现有媒体内核。
5. 使用现有正式构建、签名与升级方式逐节点交付。各项目先独立验证；联合测试仍由用户安排。

一步到位指首期的执行边界正确，不以宿主注入的临时实现交付为强隔离。各平台仍小步验证和提交，不要求完成一套庞大虚拟化平台才修已定位问题。

## 验收

同时在宿主与工作区执行明确不同的输入：宿主保留自己的焦点、中文组词、鼠标、剪贴板和音频设置；AI 在工作区完成点击、拖动、文本和快捷键，实际结果只出现在目标环境。模拟器或语义调用成功不替代该并行实测。

另行验证持久登录、任务文件边界、窗口关闭、网络切换、工作区重启和媒体恢复。记录可用能力、共享资源和实际限制。Android profile 没有与 VM 相同的内核边界，设备不支持专用空间时不能标为该路线验收通过。

保留现有一条 main 和一个主工作目录；只在完成各自相关检查后提交、推送并核验。虚拟化准备沿用已有设备维护授权，不中断另一项目的在途任务，联合验收仍按用户安排。
